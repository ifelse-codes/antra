One upgrade-path fix (C23), two first-impression fixes (C17, C18) and one misleading message (C22). Everything here landed on `main` between v0.6.3 and this release, over 2026-09-30 → 2026-10-02, driven by a launch-readiness pass and one manual "use it like a stranger" run.

## C23 — the upgrade path was broken, and it looked exactly like "`antra trust` is broken"

**The most serious defect Antra has shipped so far.** If you upgraded to a
CA-rotating release and ran `antra trust`, it *succeeded* — and then every
domain you had already opened warned in the browser: the leaf certificate
cached on disk was still signed by the **retired** CA, and a running daemon
never reloaded the CA at all. Re-running `antra trust` could not help, because
the rotation is exactly the thing that had already succeeded. The only cure was
deleting `~/.config/antra/certs` (macOS: `~/Library/Application Support/antra/certs`)
and restarting the daemon. Domains first seen *after* the rotation worked fine —
that asymmetry is what made it read as a trust problem rather than a caching one.

Two independent causes, both fixed and both verified by mutation:

1. a running daemon never reloaded the CA — it now re-reads it on every new
   hostname and drops leaves signed by the old one;
2. leaf certificates on disk were never checked against the current CA — they
   are now purged when the CA that signed them is no longer the current one.

The class of bug this hid in ("upgrade breaks everything already in use") is now
covered by `tests/ca_rotation.rs`: two tests, one per cause, which rotate the CA
under a **live** daemon through the real HTTPS server, each confirmed to fail
against its own cause and pass against the other. Something in CI now rotates
the CA underneath a daemon on every run.

## C17 — `antra dev` on a busy port named the wrong fix

A first `antra dev` of a Flask app on a macOS laptop hits port 5000, held by
AirPlay Receiver — and Antra said *stop the process on that port*, which no user
can, and asked whether they meant `antra alias`, which would have routed their
domain to AirPlay. The busy-port message now names the actual holder (`lsof +c 0`)
and gives advice that fits it: AirPlay Receiver → turn it off in System Settings
or use a free `--port`; anything else → who holds it, and when adding an alias
is actually safe.

## C18 — the installer showed raw `\033[…m` escape codes

Ten lines of the curl-installer used plain `echo` on colour variables, so the
very first thing a new user saw in the trust prompt was literal text like
`\033[1mTrusting the CA\033[0m`. Reported 2026-09-07, unfixed through four
releases, because no test asserted what the installer prints. A `say()`
helper now interprets the escapes, and `tests/installer_output.sh` keeps it
that way.

**`antra trust --remove --yes` also ignored `--yes`**: the router matched
`--remove` before reading `--yes`, so every scripted uninstall hit the
interactive prompt, read EOF, said "Skipped. CA remains trusted." and exited 0.
The routing is now a pure `action_for()` with covering unit tests.

## C22 — `antra trust` contradicted itself

`antra trust --user-level` could print *already trusted* and, two lines later,
*Current Antra CA is absent from all applicable trust stores* — both true, but
about two different certificates: the rotation-cleanup helper shared with
`trust --remove` had a hardcoded message. It now names the certificate it
actually removed.

## Known gap: Linux Chromium and Firefox

On Linux, `antra trust` installs the CA into the system store
(`/usr/local/share/ca-certificates`), which `curl` uses — but **Chrome and
Firefox read `~/.pki/nssdb` directly**, so on first run they still show
`ERR_CERT_AUTHORITY_INVALID` / `SEC_ERROR_UNKNOWN_ISSUER` even after a
successful trust. This ships as a known, standing assertion: the automated
browser check reproduces it on every run rather than letting it drift back
unnoticed.

**Workaround** (needs `libnss3-tools`):

```bash
sudo apt-get install -y libnss3-tools
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," \
  -n "Antra Local CA" -i ~/.config/antra/ca.pem
```

Firefox keeps its own NSS database (`~/.mozilla/firefox/<profile>`), so the same
`certutil` applies with `-d` pointing at that profile if you prefer not to open
the browser's own import dialog.

## Checked

- `tests/ca_rotation.rs` rotates the CA under a live daemon and asserts HTTPS
  survives, in CI, on every run. The blind spot that hid C23 is now covered
  rather than remembered.
- The four shell e2e suites and the Rust suite run in CI on macOS, Ubuntu and
  Windows; the automated browser check runs on macOS and Ubuntu on every push
  and PR, and explicitly attributes what each browser line proves.
- Chrome on macOS, verified 2026-10-02 on a real machine with a real login
  keychain: `antra trust --user-level` trusted (fingerprint matches), curl over
  the proxy 200, and the system Google Chrome loaded `https://<domain>/` with
  **no certificate warning**.
- Firefox is not installed on the 2026-10-02 macOS test machine, so the Firefox
  side there is a measured gap. Linux Chrome/Firefox is the open gap above.
