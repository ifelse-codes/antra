Two first-run fixes found by watching a stranger use Antra (C24, C25), plus the installer's output check now running in CI (C26). Everything here landed on `main` after v0.6.4, on 2026-10-03, and was reproduced against the released v0.6.4 binary before it was fixed.

## C24 — a server with a hardcoded port got a 503 that blamed it

Plenty of servers ignore the `PORT` Antra passes in — an ordinary
`listen(3000)` in Node is enough. `antra run` without `--port` would assign
one (say 4000), print the URL as ready, and every request then got:

```
503 Service Unavailable
Error:    Connection to 127.0.0.1:4000 refused — is your server running?
2. Start it: antra run --domain myapp.localhost --port 4000 -- <your-command>
```

The server *was* running — on 3000 — and the suggested fix repeated the wrong
port. It never recovered on its own.

**Now:** when Antra had to pick the port itself and nothing answers there, it
asks the OS which port your server is really listening on (macOS and Linux),
moves the route there after a few seconds, and tells you the flag for next
time:

```
⚠ Your server is listening on port 3000, not on the assigned port 4000 (it ignores $PORT).
✓ Route updated: myapp.localhost → port 3000
⚠ Next time, skip the guess: antra run --domain myapp.localhost --port 3000 -- node server.js
```

If the assigned port starts answering later (a dev command that starts an API
first and the app second), the route moves back by itself. If your server
listens on several ports, Antra lists them and lets you choose.

**The 503 page tells the truth.** Instead of asking whether your server is
running, it checks: *running, but listening on port 3000, not 4000*;
*running, but nothing answers yet*; or *the process has exited*.

## C25 — a route outlived its process after a hard kill

After `kill -9` or a closed terminal, `antra run` gets no chance to clean up.
The route stayed: `antra list` showed it, `antra doctor` counted it as
active, and the daemon never idled out. **The daemon now removes such routes
within 5 seconds.** `list` and `doctor` also flag them and point at
`antra prune`, which matters if a daemon from an older release is still
running.

Two smaller bugs in the same "is this process alive?" check are fixed too: a
process owned by another user (a `sudo antra run`) was treated as dead, and a
just-killed process could be treated as still running for a few seconds.
`antra prune --help` now says what it does — it removes routes, it does not
kill servers.

## C26 — the installer's output is checked on every change

`tests/installer_output.sh` — the test that would have caught v0.6.3's raw
`\033[1m` text in the installer — now runs in CI on macOS (with the stock
bash 3.2 a `curl | bash` user gets) and Ubuntu.

## Known gap: Linux Chromium and Firefox

Unchanged from v0.6.4. On Linux, `antra trust` installs the CA into the system
store, which `curl` uses — but **Chrome and Firefox read `~/.pki/nssdb`
directly**, so they still show `ERR_CERT_AUTHORITY_INVALID` /
`SEC_ERROR_UNKNOWN_ISSUER` after a successful trust.

**Workaround** (needs `libnss3-tools`):

```bash
sudo apt-get install -y libnss3-tools
certutil -d sql:$HOME/.pki/nssdb -A -t "C,," \
  -n "Antra Local CA" -i ~/.config/antra/ca.pem
```
