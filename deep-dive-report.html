01 Understanding

One command. A real URL. Your process unchanged.

Antra is a Rust CLI and a local daemon. antra run --domain myapp.localhost -- pnpm dev spawns your process, registers a route, terminates TLS on :443 with a per-domain leaf certificate minted from a local CA, and forwards — HTTP and WebSockets verbatim. The browser sees https://myapp.localhost. No ports, no /etc/hosts for .localhost, no warnings after one prompted trust step.

The unit of configuration is your existing command. Caddy and mkcert ask you to describe your servers to a third tool. Antra wraps the server you already run and infers the rest: port detection from args, PORT and HOST injection, NODE_EXTRA_CA_CERTS for Node TLS, even a stdout watcher that follows frameworks which reassign their own port. That inversion — process-wrapping instead of config-writing — is the design's center of gravity.

The project's own rule

A local networking layer, not a platform.

No cloud. No accounts. No telemetry. No tunnels. If a feature needs a signup, it does not belong here. Root-CA installs are prompted, explained, reversible — the threat model is written down, including the MITRE technique it maps to.

01

The promise

Secure contexts, real cookies, working HMR. What localhost:5173 cannot give, wrapped around the process you already run. Phases 0–10 shipped: proxy, TLS, daemon, IPC, config, cross-platform releases.

02

The trajectory

The roadmap is explicit: zero-config antra dev across seven ecosystems, an OS service so URLs survive reboots, multi-segment TLDs for OAuth redirects. It wants to be the default way a local server is reached.

03

The stack

Tokio, hyper 1, rustls, rcgen. No OpenSSL, no Node runtime, no account. Routes live in an in-memory RwLock<HashMap>; the hot path never touches disk. MIT licensed, single binary.

Two questions I could not answer from the repository: how much of the real user base is macOS-only — the login-keychain trust code is the most cared-for code in the tree — and whether the roadmap reflects many users or one very good UX test.

02 Current state

Strong bones. Three holes in the floor.

What holds

  • The proxy's error pages name the domain, the upstream, and the exact fix commands
  • antra doctor buckets errors and warnings correctly, detects real port holders, offers one-keypress fixes
  • macOS trust flow: byte-exact keychain comparison, stale-entry pruning, bounded waits that never hang headless
  • 168 tests green, clippy clean, an adversarial e2e suite already exists
  • The install URL serves the script, not HTML — an old roadmap bug, fixed

What breaks

  • Streaming responses buffer until completion — SSE hangs
  • The stdout port-watcher panics; the flagship command needs --port to work
  • Run routes persist as static aliases — zombies survive daemon restarts
  • IPv4-only bind: ::1 refused, unrelated apps can intercept
  • Stale sockets lie: "already running", raw connection errors
  • trust --remove does not remove the login-keychain trust it installs
→ BUG 01

The body is buffered

forward.rs collects the entire upstream body before replying. An infinite stream never finishes; the browser waits forever. SSE — table stakes for AI-era dev — is unusable through the proxy.

curl, through the proxy: 0 bytes in 4s, timeout curl, direct to upstream: a tick every 1.0s, on time
→ BUG 02

The watcher panics

The stdout watcher calls send_command_sync, which builds a new tokio runtime inside the running runtime. The task dies on the first port change; the route never follows Vite's real port.

thread 'tokio-rt-worker' panicked: Cannot start a runtime from within a runtime
→ BUG 03

Routes born ownerless

run registers pid: None, so the daemon files every run route as a static alias — persisted to disk, restored on restart, un-pruneable, un-killable by --force.

kill -9 the daemon → restart: "Restored 1 route(s): test.localhost → :3000" (nothing has ever listened on 3000)
No timeouts on the proxy patha wedged upstream hangs the browser indefinitely · code
WS upgrades drop cookies, Authorization, Originauthenticated WebSockets break · code
trust --remove misses the login keychainmacOS default install path is not reversible · code
README says "This is 0.1.0"Cargo.toml says 0.2.9; CLI table omits four commands · code

None of these are architecture problems. All three core bugs are small diffs. That is the good news.

Streaming is buffered

live

A Python SSE endpoint, one tick per second, infinite. Expected: ticks arrive on time. Actual through the proxy: zero bytes until the stream ends — an infinite stream never arrives.

Direct to upstream
t+0.0s data: tick 0 t+1.0s data: tick 1 t+2.0s data: tick 2 …
Through Antra
(4.0s — nothing) curl: operation timed out 0 bytes received
×

The watcher panics on its purpose

live

A server printed one innocuous line mentioning another port. The watcher fired, warned — and died at the first IPC call. The feature built to follow Vite cannot fire once. The route survived only because the panic struck before the unregister.

stdout: Compiler ready. Config port 19999 reserved for metrics. antra: ⚠ Port changed: 18805 → 19999 (detected from output) thread 'tokio-rt-worker' panicked: Cannot start a runtime from within a runtime
×

Zombie routes survive restarts

live

Daemon killed with kill -9 mid-session. On restart it restores run-managed routes from aliases.json — pointing at ports where nothing listens. prune refuses to touch them: "static route, kept". remove needs a live daemon.

$ antra proxy start ✓ Restored 1 route(s): • test.localhost → 127.0.0.1:3000 (503 for everyone, forever)
×

IPv6 loopback is not served

live

The daemon binds 127.0.0.1 only. localhost prefers ::1 on modern macOS — and on this machine an unrelated Python process bound to *:8080 silently answered the HTTP→HTTPS redirect probe. A proxy must never lose requests to a stranger.

$ nc -z ::1 8443 → refused $ nc -z 127.0.0.1 8443 → open $ lsof -iTCP:8080 -sTCP:LISTEN antra 127.0.0.1:8080 (IPv4) Python *:8080 (IPv6 — it wins on ::1)
×

Stale sockets lie

live

After a hard daemon kill, the socket file remains. proxy start claims the daemon is "already running"; run and list print a raw OS error with no recovery path.

$ antra proxy start ✗ Daemon is already running $ antra list Error: Connection refused (os error 61)
×

Zero-config dies on scoped names

live

A package.json named @myorg/my-cool_app produces the domain @myorg/my-cool_app.localhost. The validation error is clean — but the flow is dead for half the npm ecosystem. Uppercase names pass validation, then hit a case-sensitive route table that browsers lowercase around. code

$ antra dev ✓ Detected Node.js project: @myorg/my-cool_app Error: Invalid domain '@myorg/my-cool_app.localhost'

The proxy's 502 and 503 pages are already best-in-class. The paths users hit first deserve the same care.

05 The one contribution

The pick, and why it beats the others.

→ Highest leverage

Make the flagship flow work — real route ownership and a port-watcher that cannot panic.

This and streaming break the same promise. But the watcher breaks it on the first command a new user copies from the landing page: a 503 and a raw panic, then a zombie route left behind. It is one root cause wearing three symptoms — the system does not model who owns a route.

Fixing ownership repairs prune, --force, persistence, and port-sync at once — the highest leverage per line changed, and it deepens the process-wrapping inversion instead of adding surface area. Streaming is the immediate follow-up PR, not a distant one.

A · The fix — every route gets an owner

one root cause · six files

One design gap wears three symptoms: a route has no notion of ownership, so run registers pid-less (born a persisted zombie), the watcher re-registers pid-less (and dies trying), and prune refuses to touch any of it. Give a route an owner and the symptoms disappear together — the route behaves exactly like the process it wraps.

src/routing/types.rsRoute gains managed: bool — who owns this route
src/ipc/protocol.rsRegisterRouteRequest gains managed · #[serde(default)] · PROTOCOL_VERSION → 2
src/cli/run.rs:289register after spawn · pid: Some(child) · managed: true
src/routing/registry.rs:18persist managed == false only — aliases.json holds aliases
src/util/port_watcher.rs:25await send_command · host:port only · connect-verify before switch
src/cli/prune.rs:48 · daemon/server.rs:91prune dead managed routes · warn on unreachable aliases

Follow-up PR, same week — stream, don't buffer: src/proxy/forward.rs:78 collects the whole upstream body before the first byte is sent. Return the response with its incoming body intact and SSE stops hanging. Roughly half the size of the main fix.

# Fix brief — Antra route ownership + live port sync (verified on v0.2.9)

You are working in the Antra repository: a Rust CLI + local daemon that gives
dev servers real HTTPS URLs — antra run --domain myapp.localhost -- pnpm dev.

READ AGENT.MD FIRST. Its Critical Rules are binding: Rust + Tokio + hyper 1.x
only; routes live in an in-memory RwLock<HashMap> and the request path never
touches disk; never silently modify /etc/hosts or the trust store; zero build
warnings. Antra is a local networking layer, not a platform — no cloud, no
accounts, no telemetry, no new config surface. Refactor nothing for style.

TASK — one contribution: make the flagship flow work. Three verified root
causes, one design gap (a route has no owner):

1. src/cli/run.rs:289 registers the route with pid: None BEFORE the child is
   spawned (spawn is at :372). routing/registry.rs:18 persists every pid-less
   route to aliases.json, restored on daemon restart; cli/prune.rs:48 skips
   pid-less routes ("static route, kept"). Net: every run route is born a
   zombie — it survives kill -9, serves 503 forever, and --force cannot kill
   it because there is no PID.

2. util/port_watcher.rs:25 runs inside tokio::spawn but calls send_command_sync
   (ipc/client.rs:85), which builds a SECOND tokio runtime — panic: "Cannot
   start a runtime from within a runtime". The port-follow feature dies on its
   first trigger. Its patterns are also too loose: prose like "port 19999
   reserved for metrics" flips the route.

3. routing/types.rs:5 — Route has no ownership concept, so the daemon cannot
   tell a deliberate antra alias (long-lived) from an antra run route (must
   die with its process).

CHANGES, in this order. Smallest coherent diff first; all 168 existing
tests stay green at every step.

Step 1 — Ownership. Add pub managed: bool to Route (routing/types.rs) and to
   RegisterRouteRequest (ipc/protocol.rs) with #[serde(default)]; bump
   PROTOCOL_VERSION to 2 (CLI and daemon are the same binary — no negotiation).
   alias.rs, add.rs and proxy.rs register managed: false; the IPC handler
   (ipc/server.rs) carries the field into the registry.

Step 2 — run.rs: move registration to AFTER cmd.spawn() succeeds; pass
   pid: Some(child_pid) and managed: true. Keep the existing spawn-failure
   cleanup and replaced-route restore exactly as they behave today.
   restore_previous_route (run.rs:521) re-registers managed: false — the new
   child does not own the previous mapping.

Step 3 — registry.rs: static_alias_snapshot persists managed == false routes
   only; managed routes never reach disk.

Step 4 — port_watcher.rs: await send_command(...) directly (the task is
   already async — drop the sync wrapper). Switch the route only on a
   host:port match (127.0.0.1 / localhost / 0.0.0.0 / ::1), never on bare
   "port N" prose; TCP-connect-verify the new port accepts before switching;
   re-register with the same child PID and managed: true.

Step 5 — prune.rs: prune managed routes whose PID is dead; leave static
   aliases alone. daemon/server.rs:91 — warn about restored aliases whose
   port has no listener instead of silently serving 503.

TESTS — add, do not just keep green: (a) run registers the real child PID
with managed true; (b) kill -9 the daemon mid-run, restart: nothing restored
from aliases.json; (c) prune removes a managed route with a dead PID; (d)
watcher: a host:port line switches the route, prose does not, an
unconnectable port is not switched; (e) e2e in tests/ covering (b).

VERIFY BY RUNNING, not by reasoning: cargo build (zero warnings), cargo
test, cargo clippy. Then manually: antra run --domain t.localhost -- python3
-m http.server 18999; kill -9 the daemon; antra proxy start must restore zero
routes. Then a server whose output mentions a foreign port in prose — the
route must not move.

DONE MEANS: the landing-page command works with no --port, Vite's own
port is followed, and a hard daemon kill leaves zero zombies.

D · The return

The tool keeps the promise its landing page makes.

Today, the first command a new user copies ends in a raw panic, a 503, and a zombie route. After this diff it works the way the hero copy says — one command, a real URL, your process unchanged — and the guarantees around it become truthful: prune removes what died, --force kills the real owner, a restart restores only what should survive. Two of the seven live failures in 03 retire with this one diff; the streaming follow-up retires a third.

The deeper return is trajectory, not symptoms: zero-config antra dev and the OS service — the roadmap's next acts — both sit on top of a correct route lifecycle. Build this first and every later feature inherits it. Skip it and every later feature inherits the zombies.
