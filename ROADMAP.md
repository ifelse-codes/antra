| C14 | `antra service install` is broken on Linux | **DONE** (v0.6.2) | Verified broken first, against a real `systemd --user` manager: v0.6.1 wrote the unit to `~/.config/antra/systemd/user/`, which systemd does not search, ran `enable` with no `daemon-reload`, printed `✗ Failed to enable service: Unit file antra-proxy.service does not exist`, then *"will start automatically on login"* anyway; `status` then told the user to `systemctl --user start` a unit systemd could not find. **Moving the file was not enough on its own:** `antra proxy start` forks the daemon and exits, so under `Type=simple` systemd read the exit as the service stopping, SIGTERMed the daemon with the rest of the cgroup, and `Restart=always` looped every 5 s — shown with the old unit placed on the search path (daemon up, killed, restarted, three times in 13 s). The fix: the unit goes to `$XDG_CONFIG_HOME/systemd/user/` (`dirs::config_dir()`), carries `Environment=ANTRA_DAEMON=1` so `proxy start` runs the daemon in the foreground exactly as the CLI's auto-start does, appends its output to the `antra logs` file, and carries `ANTRA_PORT`/`ANTRA_HTTP_PORT` if set at install time. Install runs `daemon-reload` → `enable` → `start`, waits for the IPC socket before saying *started* (`Type=simple` succeeds the moment it forks), rolls the file back to what it found if reload or enable fails (so a re-install over SSH cannot delete a working unit), and does not start a second daemon when one is already running outside the service — it says how to hand over instead. **Units at the old path** were never loaded, so they hold no state: install and uninstall delete them, status mentions them. Verified with a 28-check script against a real user manager: 28/0 on the fix, 10/18 on v0.6.1 (same script, same box). The script and how to run systemd in a container are in `AGENT.md`. |
| C15 | Daemon refuses to start on a host without IPv6 | **DONE** (v0.6.2) | Found while verifying C14 in the claude.ai cloud container, which has no IPv6 at all. Every listener (`proxy/https.rs`: `probe_port`, `start_server`, `bind_http_redirect`) and `util::port::is_port_available` bound `::1` and treated *any* error as "port in use", so the daemon exited with `Cannot start daemon: HTTPS unavailable (Both 443 and 8443 are in use)` on free ports and every port read as taken. `util::port::loopback_binds` now makes the one decision for all four: `::1` is dropped only for `EAFNOSUPPORT` (no IPv6 in the kernel) or `EADDRNOTAVAIL` (no `::1` configured, e.g. `disable_ipv6=1` on `lo`); `EADDRINUSE`/`EACCES` on `::1` stay errors, since shadowing another IPv6 listener on `localhost` is why `::1` is bound at all. Verified in that container with the real binary — HTTPS and the redirect serve, the Rust suite goes from 7 failures to 0, the 28 C14 service checks pass — and by five hermetic tests (CI runners have IPv6, so they could not otherwise see this path), each shown to catch a mutation. The `EADDRNOTAVAIL` case is covered by the tests only; no host with `::1` merely disabled was available. |
| C16 | macOS launchd plist respawned `proxy start` every 10 s | **DONE** (unreleased) | Confirmed on a GitHub `macos-latest` runner, the first Mac this work had: after `antra service install`, launchd ran the job **7 times in 60 s**, supervised **no pid**, and `daemon.log` gained six *Daemon is already running* entries. Verified by **Service (macOS)** (`.github/workflows/service-macos.yml` + `.github/scripts/check-launchd.sh`), which runs on every change to `service.rs`: 17/0 — fresh install (one run, launchd pid = daemon pid for 40 s, `plutil -lint`, uninstall stops the daemon), install beside a running daemon, and upgrade over a v0.6.2 plist, which the same script first shows reproducing C16. |
