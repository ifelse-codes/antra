# Antra UX Test — 2026-09-06 (retest, ~13:55 IST)

Tester: stranger-mode AI run. No source/README read for judgments below (only website, install script, CLI output, live behavior). Binary under test: `antra 0.2.1` (cargo-installed, pre-existing). Latest release per GitHub API: `v0.2.2`.

## Phase 1: Discovery (Website)

- **What does this tool do?** Gives local dev servers stable HTTPS domains (e.g. `https://myapp.localhost`) via a local daemon — no ports in URLs, no hosts-file edits, no browser cert warnings.
- **What's the promise?** "One command and you're there": `antra run --domain myapp.localhost -- pnpm dev`, then open a real URL. No cloud, no accounts, no telemetry.
- **Does the website make you want to try it?** Yes. Problem/solution framing is sharp, the comparison table vs localhost:port / mkcert+Caddy / ngrok is persuasive, quick-start is above the fold.
- **Confusing/unclear:**
  - No `antra.toml` example anywhere on the landing page, yet "Project config" is a headline capability.
  - Comparison-table row "Hosts file edits: Only for .test" is cryptic — it implies `.localhost` never needs hosts edits, but Safari on macOS doesn't resolve `*.localhost` (there is an `antra hosts sync` command that needs sudo, undiscoverable from the site).
  - No mention that ports 443/80 need sudo (or that fallback ports change the URL you visit).
- **Questions before installing:** Is `curl | bash` safe (checksum? pinned version? follows latest — yes, script does verify sha256, good)? What perks need sudo?

## Phase 2: Installation

- **How smooth was the install?** FAILED. `curl -fsSL https://antra.iifelse.com/install.sh | bash` exits 1 on Apple Silicon:
  ```
  ANTRA INSTALLER
  ✗ No release binary for darwin-aarch64
  ```
  Root cause (from script text): `detect_arch` normalizes `arm64` → `aarch64`, but `artifact_name` matches `darwin-arm64` / `linux-arm64`. The combined keys `darwin-aarch64` and `linux-aarch64` have no mapping — even though the actual release assets ARE named `antra-aarch64-apple-darwin` / `antra-aarch64-linux` (confirmed via GitHub API; assets exist for v0.2.2). So the installer is broken for **all Apple Silicon Macs and ARM Linux** — arguably the majority of the target audience. Intel Mac (`darwin-x86_64`) and Intel Linux paths look correct.
- **Did you feel confident it was safe to run?** Mostly. Script auto-detects platform, verifies sha256, installs to `/usr/local/bin` or `~/.local/bin`, and asks before trusting the CA. It follows `latest` with no version pin — fine for install, worth noting.
- **Surprises:** Never got to the trust prompt because detection died first. Brew formula (`brew install ifelse-codes/antra/antra`, stable 0.2.2) exists as a working Mac alternative, but the site lists curl first — every M-series Mac user hits the broken path first.
- Prior run (same day) reported install.sh returning HTML; that part is fixed (now serves a real script) but the script itself is broken on arm64.

## Phase 3: First Run

- **`antra --help`:** Clear. 14 commands (`run dev add list doctor trust proxy clean alias open remove prune hosts service`). Enough to orient.
- **`antra doctor` (before setup):** Actionable output with fix hints (`antra trust`, `antra proxy start`, sudo-or-fallback for 443/80). Good. Two accuracy issues found later (see Phase 7 notes):
  1. After `antra trust --user-level` succeeded (verified in login keychain AND `curl` without `-k` reporting `SSL certificate verify ok`), `doctor` and `trust --status` still report "CA NOT trusted" — they only check the system store.
  2. With the daemon on fallback ports, `doctor` shows `✓ Port 80 (HTTP redirect) — Antra daemon active`, implying port 80 works, when it doesn't.
- **Could you figure out next steps?** Yes: `antra trust` → `antra proxy start` → `antra run …`. `trust --user-level` (no sudo, macOS) is the real happy path but is only discoverable via `trust --help`, not via `doctor`.
- **Quick start from website:** `antra run` flow works (Phase 4).

## Phase 4: Core Usage

Setup: `antra proxy start` as unprivileged user → daemon on **fallback ports** `127.0.0.1:8443` (HTTPS) + `127.0.0.1:8080`, with a clear note that 443/80 need sudo. Auto-fallback (no crash) is good UX.

Worth a `doctor` collision check.

## Issues Found (ranked)

1. **install.sh arch map broken on arm64 (NEW, critical)** — `detect_arch` yields `aarch64`, `artifact_name` expects `arm64`; `darwin-aarch64`/`linux-aarch64` unmapped despite matching release assets. Every Apple Silicon + ARM Linux user fails at step one.
2. **`alias` prints unusable URL on fallback ports (NEW, high)** — says `https://host`, serves `:8443`. `run`/`add` already do this right; unify.
3. **Trust-status blind spot (NEW, medium)** — `trust --status`/`doctor` ignore user-level keychain trust; they report failure right after a successful no-sudo trust that verifiably works.
4. **`doctor` false green on port 80 (NEW, low-medium)** — checkmark while on 8080 fallback.
5. **`antra.toml` schema undiscoverable + string-command spawn bug (NEW, medium)** — no site/`--help` example; `command = "a b c"` spawns literally, registers route, then 503s. Split via shell or validate pre-registration; document `args = [...]`.
6. **`antra run` backend failure exits 0 (NEW, low)** — masks failures in scripts/CI.
7. **Daemon log reports configured ports, not bound ports (NEW, low)** — `https_port=443` while on 8443.
8. **Install URL serving HTML (prior runs) — FIXED** — now serves the real script. Replaced by issue #1.
9. **No-route TLS error (prior runs) — FIXED** — now a helpful 502 with fix steps.
10. **`trust` sudo friction (prior runs) — MITIGATED** — `--user-level` works without sudo; just needs surfacing in `doctor`/site.
