## Findings

### 1. The installer prints its own colour codes (fixed on this branch)

Ten lines use `echo` with `${BOLD}`-style variables. `echo` does not interpret
`\033`, so a new user sees:

```
  \033[1mTrusting the CA\033[0m means HTTPS works with zero browser warnings — forever.
```

First reported 2026-09-07 in `user-test-2026-09-07-1430.md`, and it survived
four releases. It is in the trust prompt and in the quick-start block, so it is
on screen during the two moments a first-time user is reading most carefully.

### 2. `antra run` cannot infer a port, and the auto-assigned one is wrong

```
⚠ Could not detect port from command. Auto-assigned port 4000.
✓ Route registered: hard.localhost → 127.0.0.1:4000
→ https://hard.localhost:18999
```

Then `https://hard.localhost:18999/` returns:

```
503 Service Unavailable
Upstream: 127.0.0.1:4000
Error:    Connection to 127.0.0.1:4000 refused — is your server running?
```

The app **is** running, on 3000. Antra registered a port nothing was listening
on, printed the URL as though it were ready, and then blamed the user's server
for not answering. Three things are wrong:

- the warning is easy to scroll past, and everything after it looks like success;
- the 503 says "is your server running?" when it is running — the message is
  actively false;
- the fix is one flag, already shown in the tip, and never repeated at the
  point of failure where it is needed.

How common is this? `PORT` injection only helps a server that reads
`process.env.PORT`. A hardcoded `listen(3000)` is ordinary Node, and it is
commoner than the `PORT`-reading form. When Antra auto-assigns, it is guessing.

Not a release blocker — the tip is technically correct and the journey works if
you read the warning. But it is the first-run experience for a large slice of
users, and the 503 actively sends them the wrong way.

**Suggested:** when the port was auto-assigned rather than detected, say so at
the failure point too, and make the 503 name the possibility that the route and
the server disagree about the port.

### 3. A stale route survives a hard kill

`antra list` kept showing a route whose PID was dead, after the process was
`pkill`ed rather than interrupted:

```
myapp.localhost   4000   27585   48s     ← kill -0 27585: no such process
```

Ctrl+C is clean (finding 12). A `SIGKILL`, or a terminal closing without
interrupting, leaves the entry until the next `antra run` on that domain — and
it still counts as a live route in `doctor`.

Worth noting as a *known* behaviour rather than a bug: a hard kill gives the
process no chance to clean up. But `antra doctor` reporting a dead route as
active is a false all-clear, and `antra prune` exists for exactly this. The
stranger-facing question is whether anything tells you to run it.

### 4. Linux Chrome and Firefox still warn after `antra trust` (open, by decision)

Not reproducible on this Mac. From the 2026-09-30 probe, reproduced with
Playwright's Chromium in a Linux container: `antra trust` writes
`/usr/local/share/ca-certificates`, which `curl` reads and Chrome does not.
Chrome and Firefox read `~/.pki/nssdb`. The page fails with
`net::ERR_CERT_AUTHORITY_INVALID` until the CA is added there with `certutil`.

Phase 6 excludes NSS modification, so this stands. The consequence is that the
product's headline promise does not hold on Linux in the two most common
browsers, and only a browser reveals it — `curl` is green. `.github/scripts/
check-browsers.sh` now records it as an expected failure on every run, so it
stays visible rather than being forgotten.

**Suggested for v0.6.4 notes:** state it. The installer says "zero browser
warnings — forever", and on Linux Chrome that is not yet true.

### 5. The installer's download did not finish

```
▸ Downloading antra-aarch64-apple-darwin (v0.6.3)...
```

No progress after several minutes, and the script was still running when the
test was stopped. This may be nothing — a slow or throttled network on the test
machine, or a proxy in front of it. It is **not** claimed as a bug: I did not
verify it, and the same script has installed correctly in CI's Release Check.

It is recorded because a stranger who hits it sees the installer hang on its
very first action, and because nobody has watched this script run to completion
by hand in a while. Worth one clean run from a fresh `HOME` on an ordinary
network before v0.6.4.

---

## Verdict

The product works. A real HTTPS URL, a real certificate, correct redirect, a
clean Ctrl+C, an honest `doctor`, and a `trust --remove --yes` that now does
what it says. The two things standing between this and a clean first run are
both about *messages*: the installer printing its own escape codes, and a port
heuristic that guesses and then blames the user when the guess is wrong.

Nothing here blocks v0.6.4. Findings 1 and 4 belong in it; 2 and 3 are worth
filing; 5 needs one human run of the installer to settle.

## Follow-up — 2026-10-03

All three open findings were reproduced against the released v0.6.4 binary
in the cloud container (Linux), then fixed. Details in ROADMAP C24–C26.

| Finding | Status |
|---|---|
| 2. Auto-assigned port, then a 503 that blames the server | **Fixed (C24).** A silent `listen(3000)` server: v0.6.4 gave 503 for all 12 s polled, and its fix line said `--port 4000`. Now the route moves to 3000 after 5 s and the terminal prints `--port 3000` for next time; any 503 names the port the server really holds. |
| 3. Stale route after a hard kill | **Fixed (C25).** v0.6.4 still listed it, and `doctor` counted it active, 9 s after `kill -9`. Now the daemon removes it within 5 s; `list` and `doctor` flag it until then and point at `antra prune`. |
| 5. Installer download stalled | **Clean on Linux (C26).** From a fresh `HOME`: 1.9 s, hash equal to the release asset, no `\033` text. Not re-run on macOS, where the stall was seen. |
