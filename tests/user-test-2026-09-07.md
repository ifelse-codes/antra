# Antra UX Test — 2026-09-07 (retest, morning IST)

Tester: stranger-mode AI run. Judgments below use only the website, install script, CLI `--help` output, and live behavior (source/README not consulted for conclusions). Binary under test: `antra 0.2.4` (`~/.local/bin/antra`, matches latest GitHub release `v0.2.4`). Prior retest (2026-09-06 ~17:45 IST) tested 0.2.3 — this run verifies those fixes on 0.2.4 and re-runs all 7 phases.

## Phase 1: Discovery (Website)

- **What does this tool do?** Gives local dev servers stable HTTPS domains (e.g. `https://myapp.localhost`) via a local daemon — no ports in URLs, no hosts-file edits, no browser cert warnings.
- **What's the promise?** "One command and you're there": `antra run --domain myapp.localhost -- pnpm dev`, then open a real URL. No cloud, no accounts, no telemetry. Rust, local-only.
- **Does the website make you want to try it?** Yes. Problem/solution framing ("Local development still looks like 2009"), comparison table vs localhost:port / mkcert+Caddy / ngrok, architecture diagram, and `antra.toml` example are persuasive. Install is one curl line plus a brew alternative.
- **What's confusing or unclear:**
  - Comparison-table row "Hosts file edits: Only for .test" is still cryptic — implies `.localhost` never needs hosts edits, but there is an `antra hosts sync` command (for Safari) undiscoverable from the site.
  - Still no mention that ports 443/80 need sudo, or that fallback ports change the URL you visit (`:8443`). The "No ports" promise reads as unconditional.
  - No version pin in the install line (follows `latest`) — fine for trial, worth knowing for teams.
- **Questions before installing:** Is `curl | bash` safe? Mostly yes — script detects OS/arch, verifies sha256, falls back to `~/.local/bin`, asks before trusting CA. (This run found a real installer bug in that flow — see Phase 2.)

## Phase 2: Installation

- **Fetch check:** `curl -fsSL https://antra.iifelse.com/install.sh` serves the installer; `releases/latest` redirects to `v0.2.4`, matching the installed binary. Displayed arch mapping (`darwin-aarch64` → `antra-aarch64-apple-darwin`) is correct — prior arch bug stays fixed.
- **Full installer re-run (piped, as a stranger would):** re-downloaded 0.2.4, checksum verified, reinstalled to `~/.local/bin/antra` (binary timestamp updated, `--version` still `0.2.4`). So the happy path works.
- **NEW BUG — installer stdout pollution breaks `installed_path` (medium):** `install_binary()` prints status via `ok "Installed to ..."` to **stdout**, and the caller captures with `installed_path="$(install_binary ...)"`. The captured value therefore contains the colored status line plus the path. Observed consequence in the piped run:
  - `✓ Antra v0.2.4 is ready!` line was empty/garbled,
  - trust step logged `bash: line 230: ✓ Installed to /Users/.../.local/bin/antra: No such file or directory`,
  - CA auto-install then failed (`You can run 'antra trust' later`). The binary itself was correctly copied, so the damage is confusing output + skipped trust, not a broken install. Fix: print status to stderr (`ok ... >&2`) and echo only the path to stdout.
- **Non-interactive trust behavior:** when piped with no `/dev/tty`, the script prints `/dev/tty: Device not configured`, then auto-attempts CA install (which needs sudo and fails in this env). Auto-installing a trust change without an explicit yes in a non-interactive context is questionable; safer to skip with a "run `antra trust` later" hint (the `run` command already uses that pattern).
- **Safe-to-run feel:** mostly yes — platform detection, checksum verification, PATH warning, asks before trusting in TTY mode. Point off for the non-TTY auto-trust attempt and the garbled path bug.

## Issues Found (ranked)

1. **Installer `installed_path` stdout pollution (NEW, medium)** — `install_binary()` prints `ok "Installed to …"` to stdout; `installed_path="$(install_binary …)"` captures it plus the path. Piped run showed garbled `✓ Antra … ready!`, `No such file or directory` on the trust step, and skipped CA trust. Fix: `ok … >&2`, echo only `$dest` to stdout.
2. **`run` silently clobbers existing domain, then deletes the working route (NEW, medium-low)** — no replace-warning (unlike `alias`), backend crashes with raw traceback, route auto-removed leaving zero routes for that domain. Add `alias`-style warning / `--force` gate + port pre-flight + friendly error.
3. **Invalid domain suggests sudo instead of failing validation (NEW, low-medium)** — `antra alias "not a domain"` → `Permission denied writing /etc/hosts … Re-run with: sudo …`. Validate domain shape before privileged writes.
4. **`proxy start` stale "(No routes registered…)" while routes persist (NEW, trivial)** — start message contradicts `status`/`list` (4 routes restored). Print the restored count instead.
5. **`doctor` error/warning count mismatch (carried over, trivial)** — daemon-stopped state says "3 error(s)" for `⚠` items; daemon-running state says "2 warning(s)" for the same ports. Unify.
6. **`antra open` bare-URL (prior #1) — FIXED** ✅ Now prints `:8443` on fallback.
7. **Alias persistence across restart (prior #4) — FIXED** ✅ Routes survive `stop` → `start`.
8. **`add` double output (prior #6) — FIXED** ✅ Single block now.
9. **`prune` PID-less scare line (prior #7) — FIXED** ✅ Now `(static route, kept)`.
10. **Stale-trust false green / `trust` idempotency (prior #2–3) — NOT re-tested** this run (would require CA regeneration; keychain currently holds exactly 1 "Antra Local CA" entry, working).
11. **Site still silent on sudo/443 + Safari/hosts caveats** — carried over.
